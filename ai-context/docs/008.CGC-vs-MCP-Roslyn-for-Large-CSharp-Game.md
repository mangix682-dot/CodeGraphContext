# 008. CodeGraphContext vs 纯 MCP C# Roslyn：百万行 C# 游戏项目对比

> **场景假设**：一个纯 C# 的大型游戏项目，约 **100 万行代码**，包含多个 `.sln` / `.csproj`，大量继承层次、跨程序集调用、Unity/自研引擎框架代码。
>
> **对比对象**：
> - **CGC（CodeGraphContext）**：图数据库 + Tree-sitter + SCIP(Roslyn) 混合索引，通过 MCP 或 CLI 暴露给 AI
> - **纯 MCP Roslyn Server**：直接用 Roslyn 语义模型（`Microsoft.CodeAnalysis`）实时响应 MCP 工具调用

---

## 0. 一句话结论

CGC 的核心优势是 **"编译一次、查询无限次"** 的离线图谱模型，在百万行规模下，用 **预计算的图数据库** 替代 Roslyn 的实时语义分析，换来数量级的查询速度提升和全局关系可达性。

---

## 1. 架构差异总览

| 维度 | CGC | 纯 MCP Roslyn |
| :--- | :--- | :--- |
| **索引时机** | 离线预构建（`cgc index`），结果持久化到图数据库 | 每次启动加载 Solution，保持 Roslyn Workspace 常驻内存 |
| **查询引擎** | 图数据库 Cypher 查询（KuzuDB / Neo4j / FalkorDB） | Roslyn Semantic Model API（`FindReferencesAsync`、`GetSymbolInfo` 等） |
| **语义精度来源** | SCIP-dotnet（底层仍是 Roslyn）+ Tree-sitter 补充 | 原生 Roslyn，完整类型推断 |
| **内存模型** | 图数据库嵌入式（KuzuDB ~百 MB）或外置 | Roslyn 全 Solution 加载（百万行 ≈ 4–12 GB RAM） |
| **增量更新** | `cgc watch` + 文件级增量重索引 | Roslyn 增量编译（文档级） |

---

## 2. CGC 的核心优势

### 2.1 查询性能：毫秒级 vs 秒级

| 查询类型 | CGC（图数据库） | 纯 Roslyn |
| :--- | :--- | :--- |
| "谁调用了 `PlayerController.TakeDamage`？" | **Cypher 索引查询 < 10ms** | `FindReferencesAsync` 需遍历全 Solution，百万行 ≈ 2–15s |
| "从 `GameManager.Start` 到 `NetworkSync.Send` 的完整调用链" | **图遍历 `MATCH path = (a)-[:CALLS*]->(b)` < 100ms** | Roslyn 无内置调用图，需递归 `FindReferences` × N 层，**可能 > 30s** |
| "找出所有死代码" | **`MATCH (f:Function) WHERE NOT ()-[:CALLS]->(f)` 一次扫描 < 500ms** | 需对每个符号做引用搜索，**百万行可能 > 10min** |
| "所有继承自 `BaseWeapon` 的类" | **`MATCH (c)-[:INHERITS*]->(base {name:'BaseWeapon'})` < 50ms** | `FindDerivedClassesAsync` 较快但仍需全 Solution 遍历 |

**关键差异**：Roslyn 是为 **编辑器实时补全** 设计的逐文件分析引擎，不是为全局关系遍历优化的。CGC 把关系预计算成图的边，查询时只做图遍历。

### 2.2 内存占用：可控 vs 膨胀

```
百万行 C# 项目内存占用估算：

CGC (KuzuDB 嵌入式)：
├── 索引时：Python 进程 ~500MB（Tree-sitter + SCIP 临时）
├── 查询时：KuzuDB 常驻 ~100–300MB（磁盘映射）
└── MCP Server 进程：~50MB

纯 Roslyn MCP Server：
├── MSBuildWorkspace.Open()：4–12 GB（全部语法树 + 语义模型）
├── 首次加载时间：60–180s（restore + compile）
└── 持续占用：GC 压力大，可能触发 Full GC 卡顿
```

对于 100 万行的游戏项目，Roslyn 的内存占用可能直接吃掉开发机可用内存的一大块，尤其是同时运行 Unity Editor / Rider 的情况下。CGC 的图数据库是磁盘映射，查询时按需加载。

### 2.3 全局关系可达性：图原生 vs 需手动拼接

CGC 的图模型天然支持 **多跳关系查询**，这是 Roslyn API 最薄弱的环节：

```cypher
-- 影响分析：改了 NetworkManager.SendPacket，哪些上层逻辑会受影响？
MATCH path = (caller:Function)-[:CALLS*1..8]->(target:Function {name: 'SendPacket'})
WHERE caller.path CONTAINS 'GameLogic'
RETURN [n IN nodes(path) | n.name] AS call_chain, length(path) AS depth
ORDER BY depth

-- 模块耦合度：哪两个目录之间调用最频繁？
MATCH (a:Function)-[:CALLS]->(b:Function)
WHERE a.path CONTAINS 'Combat/' AND b.path CONTAINS 'Network/'
RETURN count(*) AS cross_module_calls

-- 圈复杂度 Top 20（代码质量）
MATCH (f:Function)
WHERE f.cyclomatic_complexity > 15
RETURN f.name, f.path, f.cyclomatic_complexity
ORDER BY f.cyclomatic_complexity DESC
LIMIT 20
```

纯 Roslyn 要实现上述查询，需要：
1. 手写递归 `FindReferences` 爬调用链
2. 自己维护访问过的符号集（避免循环）
3. 自己聚合统计逻辑

而 CGC 只需一条 Cypher。

### 2.4 AI 友好性：结构化图谱 vs 原始符号流

| 维度 | CGC | 纯 Roslyn |
| :--- | :--- | :--- |
| **MCP 工具数** | 21 个专用工具（`find_code`、`analyze_code_relationships`、`find_dead_code` 等） | 需自行设计工具，通常 3–5 个通用工具 |
| **返回格式** | 结构化 JSON（函数名、文件路径、行号、调用链） | 需自行序列化 Roslyn `ISymbol` 对象 |
| **上下文窗口效率** | 图查询精确返回相关节点，token 消耗少 | Roslyn 返回大量元数据，需裁剪 |
| **自然语言路由** | `analyze_code_relationships(query_type, target)` 一个工具覆盖多种分析 | 每种分析需单独的 Roslyn API 调用序列 |

AI 大模型每次 MCP 调用的 token 预算有限。CGC 的工具设计让 AI 用一次调用就能拿到 **"谁调用了这个函数 + 调用链 + 行号"** 的完整结果，而 Roslyn 方案通常需要多轮交互。

### 2.5 可视化与调试

CGC 内置：
- **交互式代码图谱可视化**（2D/3D 力导向图、城市地图、Mermaid 流程图）
- **CLI 一键分析**：`cgc analyze chain Start Send --viz` 直接生成 HTML
- **Web 浏览器在线探索**：上传代码或粘贴 GitHub URL 即可查看

纯 Roslyn MCP Server 不提供任何可视化，需要另外集成。

### 2.6 离线 & 可分享：Bundle 机制

```bash
# 导出图谱为 .cgc 文件（包含所有节点和边）
cgc bundle export --output my-game.cgc

# 另一台机器 / CI 环境直接加载，无需重新编译
cgc bundle import my-game.cgc
```

- 团队成员无需各自跑 `dotnet build` + 索引，直接加载 `.cgc` Bundle
- CI/CD 中可以自动生成 Bundle 作为制品
- Roslyn 方案每台机器都要完整加载 Solution

### 2.7 多语言支持（游戏项目常见）

游戏项目很少是纯 C#，通常还有：
- **Lua**（热更新脚本）
- **C/C++**（原生插件、引擎底层）
- **TypeScript/JavaScript**（工具链、Web 后台）
- **Python**（构建脚本、数据处理）
- **Shader 文件**（HLSL/GLSL，未来可扩展）

CGC 支持 **20 种语言** 的统一图谱，一个 `cgc index` 就能把 C# 主工程和 Lua 脚本、C++ 插件一起索引到同一个图数据库。Roslyn 只能处理 C#。

## 3. 纯 Roslyn 的优势（CGC 的局限）

公平起见，纯 Roslyn 在以下场景仍有优势：

| 维度 | 纯 Roslyn 优势 | CGC 现状 |
| :--- | :--- | :--- |
| **类型推断精度** | 完整的类型系统，泛型解析、重载决议 100% 准确 | SCIP-dotnet 基于 Roslyn 但不保留完整类型信息；Tree-sitter 纯语法层面 |
| **实时性** | 文件保存后 Roslyn 增量编译，秒级更新 | `cgc watch` 支持增量更新，但需重新解析整个文件 |
| **重构支持** | `Renamer.RenameSymbolAsync` 等原生重构 API | CGC 是只读图谱，不支持代码修改 |
| **编辑器集成** | 补全、诊断、Go-to-Definition 等 LSP 能力 | CGC 不是 LSP，不替代 IDE 的编辑功能 |
| **编译错误感知** | 能感知编译错误并提供诊断 | CGC 依赖 `dotnet build` 成功，编译失败则 SCIP 无法运行 |

> **注意**：如果借鉴 CGC 的「代码→图数据库→AI 查询」架构思想，但底层用 **原生 Roslyn** 替代 Tree-sitter + SCIP，则以上所有 Roslyn 优势都可以通过 MCP 工具暴露给 AI——同时保留图数据库的毫秒级全局查询能力。这就是「双模架构」：图数据库负责全局结构查询，Roslyn Workspace 负责实时语义/重构/诊断。详见 `009.RoslynGraphContext-Architecture-for-CSharp-Game.md`。

## 4. 百万行规模下的实际考量

### 4.1 索引时间

```
100 万行 C# 项目首次索引：
├── scip-dotnet（Roslyn 编译 + 生成 index.scip）：5–15 分钟
├── CGC 解析 index.scip + 写入图数据库：2–5 分钟
├── Tree-sitter 补充（复杂度、源码）：1–3 分钟
└── 总计：约 10–25 分钟（一次性）

后续增量更新（cgc watch）：
└── 单文件变更：< 5 秒
```

纯 Roslyn 首次加载 Solution 也需要 1–3 分钟（restore + compile），但之后**每次查询都要实时计算**。CGC 是**一次索引，无限次快速查询**。

### 4.2 推荐架构

对于百万行 C# 游戏项目，**最佳实践是 CGC + IDE Roslyn 并行**：

```
┌─────────────────────────────────────────────────┐
│                开发者工作流                        │
│                                                 │
│  Rider / VS + Roslyn LSP                        │
│  └── 实时补全、诊断、Go-to-Definition（编辑用）    │
│                                                 │
│  CGC MCP Server                                 │
│  └── AI 助手用：全局调用链、影响分析、死代码、     │
│      复杂度排查、跨语言依赖追踪（分析用）          │
│                                                 │
│  两者互补，不冲突                                 │
└─────────────────────────────────────────────────┘
```
