# 015. RoslynGraphContext 在 2.7M 行 C# 游戏项目里的实际价值评估

> **场景设定**：单个 C# 游戏项目，约 2.7M 行代码（典型大型 Unity / 自研引擎项目规模）。评估 `@d:/ai-lab/CodeGraphContext/ai-context/docs/009.RoslynGraphContext-Architecture-for-CSharp-Game.md` 描述的 RoslynGraphContext 工具对**程序员日常查询**和 **AI / MCP 接入**两类用户的实际帮助。

## 1. 2.7M 行 C# 游戏是什么概念

| 维度 | 估计值 |
| :--- | :--- |
| 文件数 | ~8,000–15,000 个 `.cs` |
| 类型数 | ~50,000–80,000（class + struct + interface + enum） |
| 方法数 | ~250,000–400,000 |
| 调用边 | ~1.5–3M |
| Token 化（GPT 估算） | **~50,000,000 tokens** |
| 全量 grep 一次 | 30s–2min（SSD），受文件系统抖动影响 |

**关键事实**：50M tokens 远超任何 LLM 上下文窗口（Claude 200k、Gemini 2M），意味着 **AI 无法在没有外部索引的情况下"看到"整个代码库**。

参考量级：

- Unity 引擎源码 ~500k LOC C++ + scripts
- Roslyn 编译器自身 ~3M LOC
- 这一规模属于"AAA 大型 / 中大型独立游戏"

## 2. AI / MCP 使用：为什么是变革性的

### 2.1 Token 经济学：必须的

```
传统做法：AI 想理解 PlayerController → 把整个 Player.cs 塞 context
2.7M 行做法：grep 50 个 .cs → 装不下 → AI 只能瞎猜

RGC 做法：一个 Cypher 查询 → 返回 200 字节 JSON → AI 答案准确
```

举例：用户问 AI "如果我改 `Inventory.AddItem` 签名，哪些代码会受影响？"

| 方案 | AI 行为 | 结果 |
| :--- | :--- | :--- |
| 无图谱 | grep "AddItem" → 找到 200 个匹配 → 装不下 → AI 瞎猜或漏报 | 错误率 30–50% |
| **RGC** | `MATCH (m)-[:CALLS]->(n {name:"AddItem"}) RETURN m` → 返回 47 条 | 几乎 100% 准确 |

### 2.2 多跳推理：一个查询 = 50 次 grep

AI 询问 "`PlayerHealth.TakeDamage` 间接触发的所有 UI 更新有哪些？"

```cypher
MATCH path = (a {name:"TakeDamage"})-[:CALLS*1..5]->(b)
WHERE b.namespace STARTS WITH "Game.UI"
RETURN path
```

无图谱：AI 需要读 PlayerHealth.cs，找到调用，跳进去再读，再跳……可能跳 5 层，每层装 1 个文件就把 context 装满了，**根本不可能完成**。

### 2.3 防幻觉：Roslyn 是 Ground Truth

C# 游戏代码的"陷阱"对 LLM 特别多：

- **Partial class** —— `MonoBehaviour` 的逻辑可能拆在 5 个文件，文本搜索看不全
- **Source generator** —— Unity 的 `[SerializeField]` 序列化代码、IL2CPP 生成代码，文本里压根没有
- **Attribute 触发** —— `[OnInspectorGUI]`、`[ContextMenu]`、`[ServerRpc]` 隐式注册的行为
- **泛型实例化** —— `ObjectPool<T>` 在哪些 T 上被实例化？

这些 RGC 在索引期都被 Roslyn 解析准确，AI 拿到的是事实而非猜测。**这一点在游戏代码里比业务代码更重要**——游戏框架（Unity/Unreal/自研）大量用编译期魔法。

### 2.4 速度

| 操作 | 无图谱 | RGC |
| :--- | :--- | :--- |
| AI 找 100 个调用者 | 30s–2min（多次 grep + 读文件） | < 50ms |
| AI 多跳分析架构 | 不可行 | 100–500ms |

LLM 调用本身就慢（5–30s/次），**外部工具响应必须毫秒级**否则交互会让人崩溃。

### 2.5 多客户端复用

写一份 MCP server，所有支持 MCP 的 AI 客户端都能用：**Claude Code / Cursor / Cline / Copilot Chat / Windsurf / Continue / 自家 ChatBot**。投入一次，全员受益。

| **命名空间耦合分析**（"`Game.UI` 跟 `Game.Audio` 互调多少次"） | ❌ | ✅ | **大** |

| **泛型实例化追踪**（"`ObjectPool<T>` 用了哪些 T"） | ❌ | ✅ | **大** |
| **代码质量排行**（"最长方法 / 最复杂方法 Top 50"） | ⚠️ Code Metrics 要手动跑 | ✅ 一行 Cypher | 中 |
| **Cypher 自定义查询**（"有 5+ 参数且体内调用 DB 的方法"） | ❌ | ✅ | **大**（小众） |
| **架构图自动生成** | ⚠️ 商业 NDepend | ✅ 免费替代 | 中 |
| **入口点追踪**（"从 `Main` 到 `EnemyAI.Update` 的路径"） | ❌ | ✅ | 中 |

## 4. 与现有工具的诚实对比

| 工具 | C# 精度 | 多跳查询 | MCP / AI | 价格 | 单机嵌入 |
| :--- | :---: | :---: | :---: | :---: | :---: |
| **VS / Rider** | ★★★★★ | ★ | ❌ | 免费 / $ | ✅ |
| **NDepend** | ★★★★ | ★★★★ | ❌ | $$$ | ✅ |
| **ReSharper Architecture** | ★★★★ | ★★★ | ❌ | $$ | ✅ |
| **Sourcegraph** | ★★★（SCIP 损失） | ★★★ | ⚠️ 自家协议 | $$ | ❌ 服务器 |
| **CGC（现状）** | ★★（SCIP 损失） | ★★★ | ✅ | 免费 | ✅ |
| **RoslynGraphContext** | ★★★★★ | ★★★★ | ✅ | 免费 | ✅ |

**RGC 唯一占住的格子**：**C# 原生精度 + 多跳查询 + MCP + 免费 + 嵌入式** —— 5 项全占的产品市场上没有。

### 4.1 为什么 CGC 不够用

CGC 通过 `scip-dotnet` 走 SCIP 协议，这条管线在 C# 上有信息损失（参考 `@d:/ai-lab/CodeGraphContext/ai-context/docs/011.CodeGraphContext-Uses-of-scip-dotnet.md` §6）：

- `enclosing_range` 不发，调用边重建靠"最近的上方 `)` 结尾的方法定义"启发式
- `kind` 字段不发，节点类型靠符号后缀启发式猜
- 泛型实例化、attribute 参数值、隐式转换协议层就丢失
- partial class 各文件独立，没有合并视图

这些损失在小项目里影响不大，在 2.7M 行规模下会累计成"AI 答案不可信"——而 RoslynGraphContext 直接吃 Roslyn `SemanticModel` 没有这个中间层损失。

### 4.2 为什么 NDepend 不够用

NDepend 是商业架构分析工具，对程序员日常查询很强（CQL 查询、依赖矩阵），但：

- **没有 MCP 接口** —— AI 用不了
- **重商业授权** —— 团队部署成本高，每个开发者要 license
- **闭源** —— 无法定制查询接口给自家 AI 客户端

NDepend 适合架构师跑大屏报告，不适合作为 AI 后端。

## 5. 投入产出比

### 5.1 工程投入

| 阶段 | 工作量 | 产出 |
| :--- | :--- | :--- |
| **v0.1 MVP**（索引 + 10 个核心查询 + MCP server） | 4–8 人周 | AI 能用，覆盖 80% 高频场景 |
| **v0.5**（完整 38 工具 + watch 增量） | +6–10 人周 | 程序员能用 + AI 全功能 |
| **v1.0**（Web Dashboard + 商业级稳定性） | +3–6 人月 | 团队级部署 |
| 运维 | < 1 人日 / 季度 | Roslyn API 升级跟进 |

### 5.2 收益模型

对于 2.7M 行项目通常 30–100 人团队来说：

```
单人 4–8 周投入 v0.1
   ↓
全队每月节省的工时（保守估计）：
  • 找代码节省 30 人 × 1h/天 × 20 天 = 600 人时/月（按 5% 时间花在"找东西"估算）
  • 架构决策更快（减少误改回滚） ≈ 80 人时/月
  • Onboarding 周期缩短 50% ≈ 200 人时/月（按每月 1 个新人估算）
   ↓
合计 ≈ 880 人时/月 ≈ 5.5 人月/月
   ↓
回本期：8 人周投入 / 5.5 人月节省 ≈ 1.5 个月
```

> 这是粗略估算。真实收益取决于团队工作模式，但**"投入越大越值得"**——因为节省随团队规模线性增长，开发投入是固定的。

## 6. 决策建议

### 6.1 建议路径（按推荐顺序）

#### 路径 A：MVP 先服 AI（推荐）

- 4–8 人周做出能给 Claude Code / Cursor / Cline 用的 MCP server
- 范围：索引 + 10 个核心查询（who_calls / what_calls / class_hierarchy / find_dead_code 等）
- 验证 AI 用例的真实价值，避免一次性投入太大
- **适合**：团队尚未确定是否值得自研，先用最小成本验证

#### 路径 B：先用现成方案试水

- 买 NDepend（架构师视角） + 用 CGC（AI 视角，即使有 SCIP 精度损失）
- 验证 2.7M 行下的真实需求，再决定是否自研
- **适合**：团队预算允许买商业工具，且不确定 AI 用例是否能落地

#### 路径 C：完整工具链

- 投入 3–4 人月做 v0.5，同时服 AI 和程序员日常，配 Web Dashboard
- **适合**：已确认有充足的 AI 辅助开发预期 + 团队架构 / 性能问题严重 + 资源充足

#### 路径 D：只做 AI 接口（最小范围）

- 彻底不管程序员日常（VS / Rider 够用），只做纯 MCP server
- **适合**：团队规模大但只想最小投入，把 RGC 定位成"AI 专用基础设施"

### 6.2 不建议自研的情况

- 团队 < 10 人，2.7M 行更可能是历史包袱而非高频开发，VS / Rider 够用
- 没有 AI 辅助开发的明确预期或文化阻力
- 没有 4 周以上的连续开发时间投入

### 6.3 强烈推荐自研的情况

- 团队 > 30 人且 AI 辅助开发已是日常工作流
- 有架构治理需求（命名空间耦合、模块依赖、死代码清理）
- 有持续 onboarding 新员工的压力
- CGC / Sourcegraph 等通用方案因 C# 精度损失不能满足

---

## 7. 一句话总结

> 对 2.7M 行 C# 游戏项目而言，**RoslynGraphContext 对 AI 是必需品、对程序员是奢侈品**。如果有 AI 辅助开发预期，回本期 < 2 个月；如果只想给程序员用，VS / Rider + NDepend 已经足够。最佳路径是**先做 MVP 服 AI 验证价值（4–8 人周）**，然后按反馈决定是否扩展。
