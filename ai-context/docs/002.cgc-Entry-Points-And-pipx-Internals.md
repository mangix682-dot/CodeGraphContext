## 1. 起点：`pyproject.toml` 的 `[project.scripts]`

来自 `@e:/claude-hub/CodeGraphContext/pyproject.toml:57-59`：

```toml
[project.scripts]
cgc = "codegraphcontext.cli.main:app"
codegraphcontext = "codegraphcontext.cli.main:app"
```

这是 **PEP 621** 定义的标准声明。语法约定：

```
<命令名> = "<可导入的模块路径>:<模块里的可调用对象>"
```

意思是「装好这个包之后，请创建一个名叫 `cgc` 的命令；它的行为等价于 `from codegraphcontext.cli.main import app; app()`」。

注意：**这只是声明，本身不是可执行文件**。真正的 `.exe` 是 `pip` 在装包时根据这条声明生成的。

同一个回调函数 `app` 同时被注册成 `cgc` 和 `codegraphcontext` 两个名字，所以你会看到 venv 里同时多出两个 `.exe`，行为完全相同（参考 `@e:/claude-hub/CodeGraphContext/src/codegraphcontext/cli/main.py:7-8` 的命令模块定义）。

## 2. `pip install codegraphcontext` 的六步

无论你直接 `pip install` 还是 `pipx install`，最终都是 pip 在 venv 内执行下面六步：

| 步 | 动作 | 落地位置（`<venv>` 表示当前虚拟环境根） |
| :--- | :--- | :--- |
| 1 | 解析依赖（看 `pyproject.toml` 的 `dependencies`） | 仅元数据，无文件落盘 |
| 2 | 从 PyPI 下载 `codegraphcontext-0.4.9-py3-none-any.whl`（一个 zip） | `<pip 缓存>` |
| 3 | 解压 wheel 内容到 site-packages | `<venv>\Lib\site-packages\codegraphcontext\` |
| 4 | 递归装依赖（neo4j、typer、kuzu、tree-sitter…） | 同上各自目录 |
| 5 | **读取 wheel 内 `entry_points.txt` → 生成命令 stub** | `<venv>\Scripts\cgc.exe` 与 `codegraphcontext.exe` |
| 6 | 写元数据（版本、文件清单、入口点） | `<venv>\Lib\site-packages\codegraphcontext-0.4.9.dist-info\` |

第 5 步就是 `.exe` 的诞生现场。下一节展开。

## 3. `cgc.exe` 内部到底是什么

### 3.1 它不是一个传统 C 程序

`cgc.exe` 通常 **80–110 KB**——这点体积根本塞不下 Python 解释器、不是 PyInstaller 打的，也不是 Rust/C++ 重写的。它的本质是：

> **一个通用启动器（C 写的小 stub）+ 末尾粘了一段 ZIP，ZIP 里是 Python 包装脚本**

### 3.2 三段式结构

`cgc.exe` 实际上是把三段二进制 / 文本拼起来的：

```
┌──────────────────────────────────────────┐  偏移 0
│  1) PE 启动器 stub                       │  ← 来自 distlib（pip 自带）
│     ~95 KB 的 64-bit Windows 程序          │     等同 pip._vendor.distlib/t64.exe
├──────────────────────────────────────────┤
│  2) shebang 行（一行 ASCII 文本）          │
│     #!"C:\Users\you\pipx\venvs\          │  ← 这行是关键！
│     codegraphcontext\Scripts\python.exe" │
├──────────────────────────────────────────┤
│  3) ZIP 归档                              │
│     里面只有一个文件 __main__.py:         │
│         import sys                       │
│         from codegraphcontext.cli.main \ │
│             import app                   │
│         if __name__ == "__main__":       │
│             sys.exit(app())              │
└──────────────────────────────────────────┘  EOF
```

stub 是 `pip._vendor.distlib` 提供的标准启动器（GitHub 上叫 `t32.exe` / `t64.exe`），所有 pip 装的命令行工具都用同一个 stub。`pip` 自身的 `pip.exe`、`black.exe`、`pytest.exe` 也是这种结构。

### 3.3 你可以亲手验证

```powershell
# 1. 大小（80~120 KB 都正常，绝不会上 MB）
(Get-Item "$env:USERPROFILE\.local\bin\cgc.exe").Length

# 2. 看末尾几个字节，能看到 PK\x03\x04（ZIP 文件头魔数）
$bytes = [System.IO.File]::ReadAllBytes("$env:USERPROFILE\.local\bin\cgc.exe")
# 找 ZIP 中央目录尾签名 (PK\x05\x06)
$end = -1; for ($i = $bytes.Length - 22; $i -ge 0; $i--) {
    if ($bytes[$i] -eq 0x50 -and $bytes[$i+1] -eq 0x4b -and
        $bytes[$i+2] -eq 0x05 -and $bytes[$i+3] -eq 0x06) { $end = $i; break }
}
"ZIP central dir found at offset: $end / total: $($bytes.Length)"

# 3. 直接把它当 ZIP 解开（Python 自己就能干）
python -c "import zipfile,sys; z=zipfile.ZipFile(r'$env:USERPROFILE\.local\bin\cgc.exe'); print(z.namelist()); print(z.read('__main__.py').decode())"
```

最后那行会输出类似：

```
['__main__.py']
# -*- coding: utf-8 -*-
import re
import sys
from codegraphcontext.cli.main import app
if __name__ == '__main__':
    sys.argv[0] = re.sub(r'(-script\.pyw|\.exe)?$', '', sys.argv[0])
    sys.exit(app())
```

这就是 stub 启动后真正运行的 Python 代码。

## 4. `cgc` 和虚拟环境的「隐形脐带」：那行 shebang

**核心问题**：你在 `C:\anywhere\` 敲 `cgc`，它**怎么知道**要去用 `~\pipx\venvs\codegraphcontext\` 这个 venv 的 Python，而不是系统 Python？

**答案**：第 3 节图里那行 shebang——它在 `pip install` 时就已经把 venv 的 `python.exe` **绝对路径**烧进了 .exe 文件本体。

启动器 stub 的工作流程（运行时）：

1. 读取自身（启动器知道自己在哪个文件）。
2. 从尾部往前扫，定位 ZIP 中央目录尾签名 `PK\x05\x06`。
3. 倒推得到 ZIP 起始位置——shebang 行就在它前面。
4. 解析 shebang，得到 `python.exe` 的绝对路径。
5. `CreateProcess(<那个 python.exe>, "<自己的路径>", ...)`，把启动器自身当 ZIP-app 喂给那个 Python 解释器。
6. Python 解释器看到第一个参数是个含 `__main__.py` 的 ZIP，就执行 `__main__.py`。
7. `__main__.py` 第一句 `from codegraphcontext.cli.main import app`——这次的 `import` 走的是那个 venv 的 `site-packages`，因为 `python.exe` 一启动就把自己所属 venv 的 site-packages 放进了 `sys.path`。
8. `app()` 跑起来，typer 解析 `--help`，输出帮助文本。

整条链路不依赖任何环境变量、不依赖 PATH、不依赖 `PYTHONPATH`——**全靠 shebang 里那个绝对路径**。

> **可视化的小实验**：用文本编辑器（如 VS Code 用 hex 模式）打开 `cgc.exe`，往后翻几页，能看到一行明文：
>
> ```
> #!"C:\Users\<你>\pipx\venvs\codegraphcontext\Scripts\python.exe"
> ```
>
> 这就是「为什么 `cgc` 永远找对 venv」的最终答案。

## 5. pipx 如何把它「全局化」

pipx 自己 **不动 .exe 内容**，它就两步事：

### 5.1 第一步：建 venv + 装包

```text
%USERPROFILE%\pipx\venvs\codegraphcontext\
├─ pyvenv.cfg                ← 标准 venv 标记
├─ Scripts\
│  ├─ python.exe             ← venv 自己的 Python（独立解释器）
│  ├─ pip.exe
│  ├─ cgc.exe                ← pip 在这里生成的原始 stub
│  └─ codegraphcontext.exe
└─ Lib\
   └─ site-packages\
      ├─ codegraphcontext\   ← 包源码
      ├─ neo4j\, typer\, …   ← 所有依赖
      └─ codegraphcontext-0.4.9.dist-info\
```

这一步等价于：

```powershell
python -m venv $env:USERPROFILE\pipx\venvs\codegraphcontext
& $env:USERPROFILE\pipx\venvs\codegraphcontext\Scripts\python.exe -m pip install codegraphcontext
```

注意：**第 4 节那个 shebang 的绝对路径里，写死的就是 `Scripts\python.exe` 这一行的位置**——pip 在装包瞬间就知道自己跑在哪个 venv，于是把 `Scripts\python.exe` 全路径焊进 stub。

### 5.2 第二步：把 stub 复制到 PATH 上的「桥头堡」

pipx 把上一步生成的两个 `.exe` 复制（Windows 没有省事的符号链接，pipx 用 `shutil.copy2`；如果你开了 Developer Mode 它会优先 hardlink）到：

```
%USERPROFILE%\.local\bin\cgc.exe
%USERPROFILE%\.local\bin\codegraphcontext.exe
```

**复制后 shebang 路径不变**——它本来就是绝对路径，搬到哪都指向 `~\pipx\venvs\codegraphcontext\Scripts\python.exe`。

`pipx ensurepath` 把 `%USERPROFILE%\.local\bin` 永久加到用户级 `PATH`。从此任何 PowerShell、cmd、IDE 子进程、Claude Code、Windows 计划任务，都能 `cgc xxx`。

> **副作用**：在 venv 里 `pip uninstall codegraphcontext` 会删掉 `~\pipx\venvs\…\Scripts\cgc.exe`，但 **不会** 删掉 `~\.local\bin\cgc.exe`（pipx 复制出去的那个独立副本）。后者会变成「无效 shim」，运行时报 shebang 路径下 python.exe 找不到。**正确做法是 `pipx uninstall codegraphcontext`**——pipx 会同时清两边。

## 6. 端到端：执行一次 `cgc --help` 时发生了什么

```
1. 你在 PowerShell 里敲 cgc --help <Enter>
2. PowerShell 在 PATH 顺序里查找 → 命中 %USERPROFILE%\.local\bin\cgc.exe
3. Windows 加载 cgc.exe → distlib stub 启动
4. stub 从自身尾部解析 shebang →
       %USERPROFILE%\pipx\venvs\codegraphcontext\Scripts\python.exe
   stub 从自身尾部解析 ZIP    →
       一个内含 __main__.py 的 zip 包
5. stub 调 CreateProcess：
       <那个 python.exe>  <cgc.exe 自己的路径>  --help
   （把 .exe 当成 zipapp 喂给 python）
6. Python 解释器启动 → 因为它在 venv 的 Scripts\ 下，自动把
       <venv>\Lib\site-packages 加到 sys.path
7. Python 执行 zip 里的 __main__.py：
       from codegraphcontext.cli.main import app
       sys.exit(app(['--help']))
8. typer.Typer 实例 app 解析 argv → 打印 cgc 命令树 + 帮助
9. sys.exit(0) → stub 返回退出码 → PowerShell 收到提示符
```

**全过程没有用到系统 Python**，也没有用到任何 `activate`。这就是 pipx 的设计目标——「外面用着像全局命令，里面隔得像 Docker」。

## 7. 备选入口：`python -m codegraphcontext`

`@e:/claude-hub/CodeGraphContext/src/codegraphcontext/__main__.py:1-5`：

```python
from .cli.main import app
```

这是 Python 的「包级 main 模块」约定。带上它之后，**只要某个 Python 能 `import codegraphcontext`，就可以**：


适用场景：

- **CI / Docker**：直接用容器里的 `python -m codegraphcontext mcp start`，不依赖 PATH 配置。
- **调试**：怀疑 `cgc.exe` 损坏时，绕过 stub 直接验证。
- **MCP 客户端在某些 OS 上拒认 `.exe` shim**：可在 `.claude.json` 里写：
  ```json

    "command": "C:\\Users\\you\\pipx\\venvs\\codegraphcontext\\Scripts\\python.exe",
    "args": ["-m", "codegraphcontext", "mcp", "start"]
  }
  ```
  这条等价于 `"command": "cgc", "args": ["mcp", "start"]`，但完全绕过 entry-point stub。本仓库的 setup_wizard 在没找到 `cgc` 时就会自动退化到这个写法（参见 `@e:/claude-hub/CodeGraphContext/src/codegraphcontext/cli/setup_wizard.py:56-69`）。

## 9. 常见误解

| 误解 | 真相 |
| :--- | :--- |
| 「`cgc.exe` 是 PyInstaller 打包的可执行体」 | 错。100KB 装不下 Python。只是 distlib 的 stub。 |
| 「pipx 用了 conda」 | 错。纯标准 `venv` + `pip`，不引入新打包工具。 |
| 「升级 cgc 要重装系统 Python」 | 错。`pipx upgrade codegraphcontext` 即可，只动 venv 内部。 |
| 「`pip uninstall codegraphcontext` 能清干净」 | 不全对。venv 里清了，但 `~\.local\bin\` 的 shim 副本还在。要用 `pipx uninstall`。 |
| 「shebang 是 Linux 专属」 | 错。Windows 上的 distlib stub **专门解析** `#!"…"` 形式的 shebang，是它工作的根本机制。 |
| 「PATH 里没有 venv，命令还能跑」 | 是的，故意的。stub 有绝对路径，根本不需要 venv 在 PATH 上。 |
| 「cgc 和 codegraphcontext 是两个不同程序」 | 同一份代码两个名字，pyproject.toml 里两条 entry-point 都指向 `cli.main:app`。 |

```json
"command": "cgc",
```

现在你应该完全理解这段配置发生的事：

## 12. 「我要改源码 / 调试本仓库」——别用 `pipx install codegraphcontext`

> **你的疑问完全成立**：上面所有讲法的前提是「从 PyPI 装的稳定版」。`pipx install codegraphcontext` **绝不会**碰 `e:\claude-hub\CodeGraphContext\src\` 下的源码——它去 PyPI 拉的是 `codegraphcontext-0.4.9.whl`，解到 `~\pipx\venvs\codegraphcontext\Lib\site-packages\` 里。**你在仓库里改一万行代码也不会反映到 `cgc` 命令上**。

开发本仓库需要换一套工作流。三种推荐姿势，按「隔离程度 → 迭代速度」排序如下。

### 12.1 方案 A：仓库内 venv + editable install（**最推荐，仓库 steering 文档同款**）

`@e:/claude-hub/CodeGraphContext/ai-context/steering/core.md:223-224` 已经把这个定为标准开发命令：`pip install -e ".[dev,parsing]"`。完整流程：

```powershell
Push-Location e:\claude-hub\CodeGraphContext

# 1. 建仓库本地 venv（每个仓库一个，不污染系统）
python -m venv .venv

# 2. 激活
.\.venv\Scripts\Activate.ps1

# 3. 编辑模式安装 + dev/parsing 额外依赖
pip install -e ".[dev,parsing]"

# 4. 验证：cgc 现在指向 .venv 里的 stub，但导入走源码
cgc --version
python -c "import codegraphcontext, pathlib; print(pathlib.Path(codegraphcontext.__file__).resolve())"
# 输出应当是：e:\claude-hub\CodeGraphContext\src\codegraphcontext\__init__.py

Pop-Location
```

**editable 是怎么做到「改源码立即生效」的？**

`pip install -e .` 不会复制源码到 site-packages。它在 `.venv\Lib\site-packages\` 里只放两样东西：

```
codegraphcontext-0.4.9.dist-info\         ← 版本元数据
__editable__.codegraphcontext-0.4.9.pth   ← 一行字：e:\claude-hub\CodeGraphContext\src
```

`.pth` 文件是 Python 启动时自动读的「额外 sys.path 文件」。Python 一启动就把 `e:\claude-hub\CodeGraphContext\src` 加进 `sys.path`，于是 `import codegraphcontext` 直接命中你的源码目录，**保存即生效，无需重装**。

`cgc.exe` 这个 stub 完全不变——它还是按第 4 节那行 shebang 找 `.venv\Scripts\python.exe`。变的只是 import 的去向。

**测试场景示例：**

```powershell
.\.venv\Scripts\Activate.ps1

# 改一行代码后：
cgc index F:\codingnet\FSAutoBuildTool      # 跑你刚改的版本
pytest tests\unit\ tests\integration\ -v    # 跑测试
python -m codegraphcontext mcp start        # 启 MCP server 调试
```

> **退出 venv**：`deactivate`。再次进来：`.\.venv\Scripts\Activate.ps1`。

### 12.2 方案 B：`pipx install --editable`（既要全局 PATH，又要改源码立即生效）

如果你希望像方案 A 一样改源码立即生效，**同时**保留 pipx 的「全局命令、独立 venv」体验，pipx 自己就支持：

```powershell
pipx install --editable e:\claude-hub\CodeGraphContext
# 或简写
pipx install -e e:\claude-hub\CodeGraphContext
```

需要 pipx ≥ 1.4。pipx 实际做的事：

1. 在 `~\pipx\venvs\codegraphcontext\` 建独立 venv（同方案 A 的 `.venv` 角色）。
2. 在 venv 里执行 **`pip install -e <你给的路径>`**——也就是把上面 12.1 节的 `.pth` 文件指向了你的仓库 `src\`。
3. 把生成的 `cgc.exe` / `codegraphcontext.exe` 复制到 `~\.local\bin\`，PATH 全局可用。

效果：

| 行为 | 表现 |
| :--- | :--- |
| 在任何目录敲 `cgc` | 命中改造过的 stub，全局可用 |
| 修改 `e:\claude-hub\CodeGraphContext\src\` 下任意 `.py` | **下次 `cgc` 调用立即生效**（Python 进程每次重新启动都会重新读源码） |
| Claude Code `.claude.json` 里 `"command": "cgc"` | 直接跑你的本地修改版 |
| 升级 PyPI 上发布的稳定版 | 不会自动覆盖（你已经把它「钉」在本地源码上） |

**和方案 A 比的差别只有一个：venv 在哪儿**——方案 A 在 `.\.venv\`（仓库目录里），方案 B 在 `~\pipx\venvs\codegraphcontext\`。方案 B 的好处是少敲一次 `Activate.ps1`，坏处是一台机器只能 `pipx install -e` 一份。

**切回 PyPI 稳定版**：

```powershell
pipx uninstall codegraphcontext
pipx install codegraphcontext
```

### 12.3 方案 C：完全不装，直接 `python -m codegraphcontext`

最快的内部循环——一行命令验证「我改的这行代码能跑通吗」：

```powershell
# 一次性：在仓库 venv 里把依赖装好（注意是 . 不是 -e）
Push-Location e:\claude-hub\CodeGraphContext
python -m venv .venv
.\.venv\Scripts\Activate.ps1
pip install -e ".[dev,parsing]"

```

之后每次：

```powershell
# venv 已经激活的情况下
python -m codegraphcontext --help
python -m codegraphcontext index F:\codingnet\FSAutoBuildTool
python -m codegraphcontext mcp start

# 或者不激活，直接用 venv 的 python：
& e:\claude-hub\CodeGraphContext\.venv\Scripts\python.exe -m codegraphcontext --help
```

`-m codegraphcontext` 走的是 `@e:/claude-hub/CodeGraphContext/src/codegraphcontext/__main__.py:1-5`，**完全绕过 entry-point stub**，最适合：

- 在 IDE 调试器里下断点（直接断到 `cli/main.py`）
- 写 PyCharm/VSCode launch.json 里的 `module: codegraphcontext`
- 容器 / CI 里跑（不用关心 PATH 配置）

### 12.4 三种方案对比

| 维度 | `pipx install codegraphcontext`<br/>（PyPI 稳定版） | 方案 A：venv + `pip install -e` | 方案 B：`pipx install -e` | 方案 C：`python -m` |
| :--- | :--- | :--- | :--- | :--- |
| 源码来源 | PyPI wheel | **本仓库 `src\`** | **本仓库 `src\`** | **本仓库 `src\`** |
| 改代码立即生效 | 否（要 `pipx upgrade`） | **是** | **是** | **是** |
| 全局 `cgc` 命令 | 是 | 否（要先 activate） | **是** | 否 |
| IDE 断点调试 | 困难 | 中等 | 中等 | **最容易** |
| 适用人群 | 终端用户 | 仓库贡献者（**推荐**） | 想全局调用本地版的开发者 | 单元测试 / CI / IDE |
| 与 Claude Code 集成 | `"command":"cgc"` 即可 | `.claude.json` 写绝对路径 `<repo>\.venv\Scripts\cgc.exe` | `"command":"cgc"` 即可 | `"command":"<py>", "args":["-m","codegraphcontext","mcp","start"]` |

**简单选择规则：**

- 只测试本仓库 → **方案 A**（最干净，符合 steering 文档约定）。
- 还要在 Claude Code 里现场试改动 → **方案 B**（一条命令搞定 PATH + 源码绑定）。
- 写测试 / 调试器调试 → **方案 C**（最直接）。
- 上面三个都不冲突，实际工作里会同时存在：A 用来跑 `pytest`，B 用来在 Claude Code 里点对话，C 用来 IDE 断点。

### 12.5 自检：我现在跑的到底是哪份代码？

**关键陷阱先讲**：在 PowerShell 里直接敲的 `python` / `pip` **不是** pipx venv 里的那个 `python.exe` / `pip.exe`，而是你 PATH 上的系统 Python。所以下面这些命令在「方案 B：pipx 安装」下**只会跑出 `ModuleNotFoundError`，不能用来验证 cgc**：

```powershell
python -c "import codegraphcontext..."           # ❌ pipx 模式下命中系统 Python，必失败
pip show codegraphcontext                        # ❌ 同理
```

正确做法分两种情况：

#### 情况 A：方案 A（仓库本地 venv，已 `Activate.ps1`）

激活态下 `python` 就是 venv 的 python，下面随便挑：

```powershell
cgc --version
python -c "import codegraphcontext, pathlib; print(pathlib.Path(codegraphcontext.__file__).resolve())"
pip show codegraphcontext | Select-String -Pattern '^(Location|Editable project location|Version):'
```

判断标准：
- `Editable project location: e:\claude-hub\CodeGraphContext` → 你跑的是仓库源码 ✓
- `__init__.py` 路径在 `e:\claude-hub\CodeGraphContext\src\…` 下 → 改代码立即生效 ✓

#### 情况 B：方案 B（`pipx install --editable …`，不需要也无法 activate）

```powershell
# 1) cgc 自身能跑（最起码能用）
cgc --version

# 2) pipx 视角看安装清单
pipx list
# 在 codegraphcontext 那行下面应当看到 "package codegraphcontext 0.4.9" 与 (editable) 字样

# 3) 用 pipx 暴露的 pip 看 editable 元数据（最直接）
pipx runpip codegraphcontext show codegraphcontext | Select-String -Pattern '^(Location|Editable project location|Version):'
# 期望：Editable project location: e:\claude-hub\CodeGraphContext

# 4) 直接调 venv 里的 python（绕过所有 PATH 干扰）
& "$env:USERPROFILE\pipx\venvs\codegraphcontext\Scripts\python.exe" -c "import codegraphcontext, pathlib; print(pathlib.Path(codegraphcontext.__file__).resolve())"
# 期望：e:\claude-hub\CodeGraphContext\src\codegraphcontext\__init__.py

# 5) 看 editable 的物证 .pth 文件
Get-Content "$env:USERPROFILE\pipx\venvs\codegraphcontext\Lib\site-packages\__editable__.codegraphcontext*.pth"
# 期望：内容指向 e:\claude-hub\CodeGraphContext\src （或 setuptools 转写后的等价路径）
```

只要 (3)(4)(5) 任意一条命中 `e:\claude-hub\CodeGraphContext`，editable 就是真生效了。

#### 终极验证：改一行真的会立即生效吗？

不管方案 A 还是 B：

```powershell
# 改 cli/main.py:2595，把版本输出后追加一段红字：
#   console.print(f"CodeGraphContext [bold cyan]{get_version()}[/bold cyan] [red][LIVE][/red]")
# 保存。然后：
cgc --version
# 应当看到：CodeGraphContext 0.4.9 [LIVE]
# 看到 [LIVE] = editable 链路通了，改一行立即反映到 cgc 调用。
```

> **常踩的坑**：同时装了 PyPI 版 + 仓库 editable 版，shell PATH 上谁先谁后决定 `cgc` 走哪份。`(Get-Command cgc).Source` 一查便知。修复办法：要么 `pipx uninstall codegraphcontext` 干掉 PyPI 那份再 `pipx install -e <repo>`，要么用方案 A 在仓库里 `Activate.ps1`，让 `.venv\Scripts\` 抢占 PATH。
