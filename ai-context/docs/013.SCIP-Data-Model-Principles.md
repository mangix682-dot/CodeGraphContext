# 013. SCIP 数据模型：结构与含义

> **一句话**：SCIP（Semantic Code Intelligence Protocol）是一份**针对代码语义的"倒排索引"协议**。它把"在某个源文件的某个位置出现了哪个符号、是定义还是引用、这个符号有什么元数据、和其它符号什么关系"打包成一个 protobuf 文件，让任何工具都能用同一份产物做跳转、查引用、查继承。
>
> 本文只讲数据结构与每条字段的**用途**，不讲具体某个语言索引器的实现。

---

## 0. 核心心智模型

整个 SCIP 协议只有 **6 个核心概念**，按从大到小嵌套：

```
Index                           ← 一次索引产物（一个仓库/工作区）
├── Metadata                    ← 这次索引本身的元信息
└── Document  (× N 个文件)      ← 一个源文件的索引数据
    ├── Occurrence  (× M)       ← "在哪里出现了什么符号、扮演什么角色、被谁包住"
    └── SymbolInformation (× K) ← "这个符号到底是个啥（文档/类型/关系）"
        └── Relationship (× R)  ← 与其它符号的关系（继承、实现、override...）
```

可以这样理解：

- **`Document`** 描述 **位置 → 符号** 的映射（"我这一行第 5 列写的是哪个符号"）。
- **`SymbolInformation`** 描述 **符号 → 元数据** 的映射（"这个符号是个方法、签名是什么、文档是什么、它实现了哪些接口"）。
- 两者通过 **符号字符串（Symbol）** 这个共同的"主键"连接。

> ⚠️ **协议里没有"调用边"消息类型**。"A 调用 B" 是从一个引用 occurrence 的 `symbol`（=callee）和它的 `enclosing_range`（=指向 caller 的定义范围）**派生**出来的，不是索引器直接存的边。详见 §5。

## 1. 符号字符串（Symbol）—— 整套协议的"主键"

SCIP 没有用数字 ID，而是用一个**人可读、机器稳定、跨索引唯一**的字符串作为符号的标识。这是协议最关键的设计。

格式（语言无关）：

```
<scheme> ' ' <package> ' ' <descriptor>+        # 全局符号
local ' ' <id>                                   # 局部符号
```

每个 `<descriptor>` 的后缀字符决定了它在符号路径中的角色：

| 后缀 | 含义 | 示例 |
| :---: | :--- | :--- |
| `/` | Namespace（命名空间/模块/包） | `System/IO/` |
| `#` | Type（类、接口、结构体、枚举……） | `List#` |
| `.` | Term（字段、属性、变量、常量……） | `Length.` |
| `(<disambig>).` | Method（方法，含重载区分符） | `Add().` 或 `Add(+1).` |
| `(<name>)` | Parameter（形参） | `(value)` |
| `[<name>]` | TypeParameter（泛型参数） | `[T]` |
| `:` | Meta（元信息，自由用途） | — |

**完整示例**：

```
scip-dotnet nuget . . Main/Classes#Add(+1).(value)
└──┬───────┘└─┬─┘└──────────┬──────────────────┘
  scheme   package        descriptors
  (谁写的)(从哪个包来的)  (命名空间→类型→方法→参数)
```

读法：「在 scip-dotnet 写的索引里、属于一个占位包、命名空间 `Main` 下的类型 `Classes` 的第 2 个 `Add` 重载（`+1` 区分符）的形参 `value`」。

### 1.1 为什么用字符串而不是 ID

- **跨索引可拼接**：仓库 A 的 `index.scip` 和仓库 B 的 `index.scip` 可以独立生成，但只要都遵守同一个 `<scheme> <package>`，就能直接对账"A 引用了 B 的某符号"。
- **稳定可复现**：同样的源码二次索引，符号串完全一样（除非源码改了）。可以做内容寻址、缓存。
- **人可读**：日志、错误消息里直接打这个字符串就能看懂。

### 1.2 局部 vs 全局

- 以 `local ` 开头的符号 **只在它所在的 `Document` 内有意义**。每个文档自己计数，跨文档不要尝试解析。典型用途：lambda 内部变量、泛型参数、局部函数。
- 其余都是全局符号，整个工作区/全网络都用这个串识别。

## 2. `Occurrence` —— 位置加角色

**含义**：源代码里某个连续的字符区间提到了哪个符号、扮演什么角色。

每个 `Occurrence` 携带 4 件事：

| 字段 | 含义 |
| :--- | :--- |
| `range` | 位置：3 元组 `[行, 起列, 止列]`（同行）或 4 元组 `[起行, 起列, 止行, 止列]`。**0 基**。 |
| `symbol` | 这一段文本指向的符号字符串。 |
| `symbol_roles` | 一个**位掩码**，标记此次出现的角色（见下表）。 |
| `range` 之外的辅助 | 语法高亮分类、override 文档、诊断信息等可选字段（很少索引器全填）。 |

### 2.1 `symbol_roles` 位含义

| Bit | 含义 | 解读 |
| :---: | :--- | :--- |
| `0x01` | **Definition** | 这里是该符号的**定义点**；缺这一位则是**引用点**。这是协议里最关键的一位。 |
| `0x02` | Import | 这里是 import/using/require |
| `0x04` | WriteAccess | 写访问（`x = 1` 里的 `x`） |
| `0x08` | ReadAccess | 读访问 |
| `0x10` | Generated | 来自代码生成 |
| `0x20` | Test | 在测试代码里 |

**最低限度要求**：索引器至少要正确设置 bit 0（Definition）。其它位是锦上添花，多数下游消费者不一定读。

### 2.2 一图说清"出现"

```
源码：    public void Greet(string name) { Console.WriteLine(name); }
位置：    ↑           ↑       ↑      ↑          ↑          ↑     ↑
角色：    定义        定义    定义   定义       引用       引用   引用
符号：    Greet()     Greet  string (name)     Console    Wri…  (name)
                              ↑                                  ↑
                         （形参定义）                      （形参引用）
```

每一个有意义的标识符都对应一个 `Occurrence`，**包括关键字之外的全部标识符**。这就是为什么一个 `Document` 通常有几十到几千个 occurrence。

---

## 3. `SymbolInformation` —— 符号的"档案卡"

每当一个符号在某个 `Document` 里**有定义**时，索引器还会发一份对应的 `SymbolInformation`，作为这个符号的元数据档案。

| 字段 | 含义 | 备注 |
| :--- | :--- | :--- |
| `symbol` | 主键（与 Occurrence.symbol 关联） | |
| `documentation` | Markdown 文档串数组 | 通常包含两段：① 用代码块包起来的签名（`public void Greet(string name)`）；② 来自源码的文档注释（如 JavaDoc/XML doc）。 |
| `kind` | 符号种类的枚举（Class/Method/Field/Interface/Enum/Variable/...） | 协议层有 60+ 种。**有些索引器不发这个字段**，下游要靠符号后缀启发式补。 |
| `display_name` | 人可读名字（用于 UI 展示） | 同上，可能空。 |
| `relationships` | 与其它符号的关系（见 §4） | 用于继承、实现、override 链。 |
| `signature_documentation` | 结构化签名信息（新版字段） | 同上，可选。 |

> **关键观察**：`SymbolInformation` **不带位置**。位置在 `Occurrence` 里。一个符号的"它定义在哪一行" = 找到该 symbol 且 `symbol_roles & 1 != 0` 的那个 `Occurrence` 的 range。这是协议刻意做的解耦：让符号元数据和源码位置分别可索引。

---

## 4. `Relationship` —— 符号间的边

`SymbolInformation.relationships` 是一个数组，每个元素是一条指向**另一个符号**的有向关系。结构很扁平：一个目标 symbol + 4 个布尔标志。

| 标志 | 语义 | 典型用途 |
| :--- | :--- | :--- |
| `is_implementation` | 我**实现/继承**了目标符号 | 类的父类链、类对接口、方法对接口方法 |
| `is_reference` | "Find references on me" 时也应包含目标 | 接口方法 → 实现方法的反向贯穿 |
| `is_type_definition` | "Go to type definition" 应跳到目标 | 变量 → 它的类型 |
| `is_definition` | 把目标也视为本符号的定义点 | 多继承字段重用同一符号时 |

最常用的是 `is_implementation`——这一位足以构造完整的"类继承树"和"接口实现关系"。

### 4.1 一个继承示例

源码：

```
interface IAnimal { void Sound(); }
class Dog : IAnimal { public void Sound() { ... } }
```

`Dog#` 的 `SymbolInformation` 会带：

```
Relationship { symbol = "IAnimal#",          is_implementation = true }
```

`Dog#Sound().` 的 `SymbolInformation` 会带：

```
Relationship { symbol = "IAnimal#Sound().",  is_implementation = true, is_reference = true }
```

`is_reference=true` 让"对 `IAnimal.Sound` 找引用"时**也**返回 `Dog.Sound` 的位置；反向不成立（对 `Dog.Sound` 找引用不会捎带 `IAnimal.Sound`）。

## 5. 调用关系：协议刻意**不**直接表达

> 仔细看 §4 会发现：`Relationship` 里没有 `is_called_by` / `is_caller_of`。这是**有意的**——SCIP 不存"调用边"。

### 5.1 调用 = 引用 occurrence + 包围范围

SCIP 把"A 调用 B"拆成**两条已有信息**的组合，让消费者自己拼：

- **被调用者 (callee)** = 那个引用 occurrence 自带的 `symbol`。
- **调用者 (caller)** = "哪个定义的范围把这个引用位置包住了"——通过 `Occurrence.enclosing_range` 告知。

```
源码:   void Foo() { Bar(); }
位置:        ↑       ↑^^
           Def     Ref (role=0)
          range    range
            ↑       │
            └───────┘
               enclosing_range  ← 引用点带的字段，标定它属于哪个方法体
```

用文字说：每个引用 occurrence 都"知道"自己被哪个定义包住了，从而隐式描述了一条 `caller → callee` 的边。

### 5.2 `Occurrence.enclosing_range`

这是 SCIP 较新版本协议加的字段，**专门为调用边重建服务**：

- 普通 `range` = 标识符本身的位置（一个标识符，几个字符）
- `enclosing_range` = 包围这个标识符的**最近一层定义**的整段范围（整个方法体、整个类体）

所以一份合格的 SCIP 索引里，每个引用 occurrence 都至少含两组坐标：「我自己在哪」+「我属于哪段定义」。消费者用后者去查定义符号表，就能回填出 caller。

### 5.3 反向 ("谁被谁调用") 怎么来

**消费者自己倒排**：把所有 `(caller, callee)` 对收集起来，按 callee 索引就是"被调用方列表"，按 caller 索引就是"它调用了谁"。SCIP 不预先存这张反向表。

这与 §7 里"Relationship 只看出向"是**同一个设计哲学**：协议只存最小、最稳定的事实，所有可派生的查询路径由消费者按需建倒排。这样：

- 索引器实现简单，只要照 AST 走一遍就行。
- 文件体积小，没有任何冗余边。
- 跨索引拼接时不会出现两侧倒排表冲突的问题。

### 5.4 一个隐含的难点：调用 vs 取地址

SCIP 的引用 occurrence **不区分** "调用 `Bar()`" 和 "把 `Bar` 当方法组取地址 / 当 delegate 传递"——它们的 occurrence 长得一模一样（同样的 `symbol`，同样的 `symbol_roles=0`）。

消费者要分清这两种，常用启发式是看**引用范围结束位置的下一个字符是不是 `(`**。这是个文本层面的判断，准确率约 95%，足够大多数图谱用途，但不是 100%。

### 5.5 旧版索引器的退化

部分较早的索引器（包括当前 `scip-dotnet`）**不发** `Occurrence.enclosing_range`。这种情况下消费者只能 fallback 用"距离引用行号最近的、上面的、以 `)` 结尾的方法定义" 来猜 caller——准确率掉一截，且会在嵌套类、嵌套方法、表达式 lambda 里出错。

这也是为什么用旧版索引器跑出的图谱里，调用边总带一点"测不准"。

## 6. `Document` —— 文件级容器

每个被索引的源文件对应一个 `Document`：

| 字段 | 含义 |
| :--- | :--- |
| `relative_path` | 相对 `Index.metadata.project_root` 的路径，用 `/` 分隔（**含 Windows**） |
| `language` | 编程语言名（`"C#"`, `"TypeScript"`, ...） |
| `occurrences` | 文件里所有出现点（**通常按位置升序，但协议不强制**） |
| `symbols` | 文件里所有定义符号的元数据档案 |

> 一个语义信息可以拆到多个 `Occurrence`，例如 `IDog#Sound()` 在文件里出现 5 次（1 定义 + 4 引用）就有 5 个 `Occurrence`。但 `SymbolInformation` 全文件最多 1 个。

---

## 7. `Index` 和 `Metadata` —— 顶层封装

| 字段 | 含义 |
| :--- | :--- |
| `Index.metadata` | 必须在流首位，整个 Index 仅一份 |
| `Index.documents` | 文件列表 |
| `Index.external_symbols` | 引用了但没在本索引里定义的"外部符号"，可附文档信息（让下游不必跨索引拉取也能 hover） |
| `Metadata.project_root` | `file://...` 形式的工作区根目录 URI |
| `Metadata.tool_info` | 索引器自报家门：名字、版本、命令行参数 |
| `Metadata.text_document_encoding` | 源文件文本编码（通常 UTF-8） |
| `Metadata.version` | 协议版本枚举 |

## 8. 协议设计要点（"为什么这样设计"）

1. **位置和元数据解耦**：`Occurrence` 只关心"在哪、是谁、什么角色"；`SymbolInformation` 只关心"这是什么、关系如何"。两侧通过符号字符串关联，可分别索引、可分别更新。

2. **符号字符串作为统一主键**：跨索引、跨仓库、跨工具都能直接拼接，不需要额外映射表。

3. **`range` 用扁平数组**：`[startLine, startChar, endLine, endChar]` 比嵌套 `Position{line, character}` 节省 50% 体积——对于动辄百万 occurrence 的大仓库，这是关键性能优化。

4. **角色用位掩码**：一个出现可以同时是 "Definition + WriteAccess + Generated"，不需要多条 occurrence。

5. **`Relationship` 只看出向**：每个 `SymbolInformation` 声明它**指向**谁，反向（"谁指向我"）由消费者自己倒排。这让索引器互相独立——A 仓库的 class 继承 B 仓库的 class，A 索引器只需写出向边，不用知道 B 里发生了什么。

6. **可选字段哲学**：`kind`、`display_name`、`enclosing_range`、`syntax_kind`、`diagnostics` 全是可选——索引器按能力选发，下游按可用性选读。这让协议向后兼容、向前兼容都成立。

## 9. 一份最小完整索引示例（含调用关系）

### 9.0 例子里出现的数字都是什么

`symbol_roles` 是个 **位掩码**，取值来自 SCIP 协议的 `SymbolRole` 枚举：

| 位值 | 名称 | 含义 |
| :---: | :--- | :--- |
| `0` | (无任何位置位) | 纯引用点 |
| `0x01` = **`1`** | **Definition** | 定义点 |
| `0x02` = `2` | Import | import / using |
| `0x04` = `4` | WriteAccess | 写访问 |
| `0x08` = `8` | ReadAccess | 读访问 |
| `0x10` = `16` | Generated | 代码生成器产物 |
| `0x20` = `32` | Test | 测试代码 |

下面例子里只出现 `0`（引用）和 `1`（定义）。多个位可叠加，例如一个生成代码里的定义点 = `1 | 16 = 17`。

`kind` 是个**枚举**，来自 `SymbolInformation.Kind`。以下例子只用三个值：

| 枚举值 | 名称 | 说明 |
| :---: | :--- | :--- |
| `7`  | **Class**     | 与类、对象、记录类型都用这个 |
| `26` | **Method**    | 成员方法 |
| `37` | **Parameter** | 形参 |

完整枚举表 60+ 项，还包括 `Interface=21` / `Enum=11` / `EnumMember=12` / `Field=15` / `Function=17` / `Constructor=9` / `Property=41` / `Namespace=30` / `TypeParameter=63` / `Module=29` / `Constant=8` / `Event=13` 等。值不连续（刚好反映了协议版本迭代增加的历史），不要试图猜数字背后的规律，查表即可。

> ⚠️ **旧版索引器（含 `scip-dotnet`）不发 `kind`**——这是较新的协议字段。这些索引器的输出里所有 `kind` 都是默认值 `0` (`UnspecifiedKind`)，下游只能靠符号后缀（`#` / `().` / `(name)`）启发式猜。

### 9.1 源文件

`Hello.cs`（0-indexed 行号）：

```
  行 0:  namespace App;
  行 1:  public class Greeter
  行 2:  {
  行 3:      public string Hello(string name) => Format(name);
  行 4:      private string Format(string s) => $"hi {s}";
  行 5:  }
```

`Hello` 调用了 `Format`。我们要看 SCIP 怎么**隐式表达**这条调用边。

对应的 `Index` 概念结构（伪 JSON，列号 0-based）：

```json
{
  "metadata": {
    "project_root": "file:///repo",
    "tool_info": { "name": "scip-dotnet", "version": "..." },
    "text_document_encoding": "UTF8"
  },
  "documents": [{
    "relative_path": "Hello.cs",
    "language": "C#",
    "occurrences": [
      // —— 命名空间 ——
      { "range": [0, 10, 13],  "symbol": "App/",                              "symbol_roles": 0 },

      // —— 类定义 ——
      { "range": [1, 13, 20],  "symbol": "App/Greeter#",                      "symbol_roles": 1,
        "enclosing_range": [1, 0, 5, 1] },                                     // 类体：行1开头到行5的 }

      // —— Hello 方法 ——
      { "range": [3, 18, 23],  "symbol": "App/Greeter#Hello().",              "symbol_roles": 1,
        "enclosing_range": [3, 4, 3, 53] },                                    // Hello 整行
      { "range": [3, 31, 35],  "symbol": "App/Greeter#Hello().(name)",        "symbol_roles": 1 },

      // —— Hello 体内：调用 Format ——
      { "range": [3, 40, 46],  "symbol": "App/Greeter#Format().",             "symbol_roles": 0,
        "enclosing_range": [3, 4, 3, 53] },                                    // ★ caller = 含同样 enclosing_range 的那个定义
      { "range": [3, 47, 51],  "symbol": "App/Greeter#Hello().(name)",        "symbol_roles": 0,
        "enclosing_range": [3, 4, 3, 53] },

      // —— Format 方法 ——
      { "range": [4, 19, 25],  "symbol": "App/Greeter#Format().",             "symbol_roles": 1,
        "enclosing_range": [4, 4, 4, 49] },                                    // Format 整行
      { "range": [4, 33, 34],  "symbol": "App/Greeter#Format().(s)",          "symbol_roles": 1 },
      { "range": [4, 45, 46],  "symbol": "App/Greeter#Format().(s)",          "symbol_roles": 0,
        "enclosing_range": [4, 4, 4, 49] }
    ],
    "symbols": [
      // 类
      { "symbol": "App/Greeter#",                    "kind": 7,  "documentation": ["```cs\npublic class Greeter\n```"] },
      // 方法
      { "symbol": "App/Greeter#Hello().",            "kind": 26, "documentation": ["```cs\npublic string Greeter.Hello(string name)\n```"] },
      { "symbol": "App/Greeter#Format().",           "kind": 26, "documentation": ["```cs\nprivate string Greeter.Format(string s)\n```"] },
      // 参数（每个参数也是一个独立符号，有自己的档案）
      { "symbol": "App/Greeter#Hello().(name)",      "kind": 37, "documentation": ["```cs\nstring name\n```"] },
      { "symbol": "App/Greeter#Format().(s)",        "kind": 37, "documentation": ["```cs\nstring s\n```"] }
    ]
  }]
}
```

### 9.2 读这份 JSON

- `symbol_roles=1` 表 Definition，`symbol_roles=0` 表 Reference。
- 每个**定义**的 `enclosing_range` 覆盖它自己的整段定义体；每个**引用**的 `enclosing_range` 覆盖**包住它的最内层定义**的整段范围。
- 行 3 出现了 4 个 occurrence：Hello 的定义、name 的定义、Format 的引用（调用点）、name 的引用——**它们都定义/引用不同的符号**。一行代码产生多个 occurrence 是常态。
- 行 3 的 Format 引用和行 4 的 Format 定义**符号串完全相同**——这正是 SCIP 连接"用法点"和"定义点"的方式。

**Occurrence 数 vs Symbol 档案数**：

- `occurrences` 包含**全部出现点**（1 个定义 + N 个引用 = N+1 条）。
- `symbols` 每个**被定义的不同符号**最多 1 条档案（与定义/引用次数无关）。
- 上例 `App/Greeter#Hello().(name)` 在 occurrences 里出现 2 次（1 定义 + 1 引用），但在 symbols 里只有 1 条档案。
- 参数 / 局部变量等"小符号"是否发档案是**可选**的——多数生产级索引器（含 `scip-dotnet`）会发，因为档案里的 `` `string name` `` 这种类型签名对 IDE hover 很有用。

### 9.3 重建调用边 `Hello → Format`

按 §5 的算法，纯靠这份 JSON 推出"Hello 调用了 Format"：

**Step 1 — 找 callee**：

扫所有引用 occurrence（role=0），找一个 symbol 看起来像方法的（以 `().` 结尾）。命中：

```
range=[3, 40, 46]   symbol="App/Greeter#Format()."   enclosing_range=[3, 4, 3, 53]
```

→ **callee = `App/Greeter#Format().`**

**Step 2 — 排除"取地址" vs "调用"**：

看引用范围结束位置 `(3, 46)` 的下一个字符——源码里是 `(`，确认这是个调用，不是 delegate 取地址。✓

**Step 3 — 找 caller**：

拿 Step 1 的 `enclosing_range = [3, 4, 3, 53]`，去 occurrences 表里找一个**定义**（role=1）且 `enclosing_range` 等于 `[3, 4, 3, 53]`。命中：

```
range=[3, 18, 23]   symbol="App/Greeter#Hello()."   enclosing_range=[3, 4, 3, 53]
```

→ **caller = `App/Greeter#Hello().`**

**结果**：从这份 JSON 派生出一条边 **`App/Greeter#Hello().` ─CALLS→ `App/Greeter#Format().`**。

### 9.4 反向 ("谁调用了 Format") 怎么来

把全工作区跑出来的所有 `(caller, callee)` 对按 callee 倒排：

```
Format()  ← {Hello()}      // 在 Hello.cs 看到这一条
Hello()   ← {…可能空…}
```

这步**消费者自己做**（构图入库时建索引），SCIP 文件里没有这张反向表。整个调用图谱就是这样从一份份 `index.scip` 里**派生**出来的——协议本身永远只存最小事实。

## 10. 实际怎么查：`.scip` 不是查询对象

> 一个自然的疑问：按 §9 那种线性 JSON，查 "X 的父类是谁" 是不是要扫整个文件？是。但 `.scip` **本来就不是用来直接查的**——它是**存储/传输格式**，不是查询引擎。

### 10.1 ETL 模式：装一次，查无数次

任何严肃的 SCIP 消费者都按"先装载再查询"的两阶段模式工作：

```
+──────────+      load       +──────────────────+      query    +──────────+
│ index.scip├────────────────▶│ 内存 / 图库 / SQL ├──────────────▶│ caller, │
│ (一次性) │    建索引       │ (常驻、可查)      │   毫秒级响应  │ 继承... │
+──────────+                  +──────────────────+               +──────────+
```

加载阶段是 O(N) 一次性投入；查询阶段是 O(log N) 或 O(度) 的高频操作。

### 10.2 三种典型加载目标

| 消费方 | 装到哪 | 找 "X 的父类" | 找 "X 的子类" |
| :--- | :--- | :--- | :--- |
| 轻量 CLI（`scip print` 等） | 内存 `dict[symbol] → SymbolInformation` | O(1) 哈希查表 | 启动期遍历一次自己倒排，之后 O(1) |
| **CodeGraphContext** | **KuzuDB 图数据库** | `MATCH (a)-[:INHERITS]->(b) WHERE a.id='X'`，走图索引 | 同上反方向查询，走反向图索引 |
| Sourcegraph 后端 | PostgreSQL 三元组表 + BTree 索引 | 按 subject 索引扫描 | 按 object 索引扫描 |

CGC 的具体做法：入库时把每条 `SymbolInformation.relationships` 展平成 `(:Class)-[:INHERITS]->(:Class)` 边（见 `@d:/ai-lab/CodeGraphContext/ai-context/docs/011.CodeGraphContext-Uses-of-scip-dotnet.md` §4）。之后所有"父类/子类/接口/实现"查询都靠 Kuzu 的图索引完成，**与原始 `.scip` 文件再也没关系**。

### 10.3 为什么协议本身不预存倒排和索引

§8.5 已讲设计哲学，落到性能上的具体动机：

1. **可流式生成**：索引器边走 AST 边吐 SymbolInformation；要预存倒排得索引完所有文件后才知道"谁继承了我"，无法流式。
2. **跨索引可拼接**：跨仓库的继承关系（A 仓的 class 继承 B 仓的 class），只有在全工作区合并后才能建倒排，单仓索引器没这个上帝视角。
3. **省体积**：倒排是 100% 冗余信息，让消费者按需建即可。一份大仓库的 `.scip` 通常已经 100+ MB，再加倒排会翻倍。

### 10.4 类比：Git 也是分层的

- `.git/objects/*` 是**存储格式**——按内容哈希存 blob/tree/commit。
- 查"这个文件历史上谁改过"——直接 grep 对象库会非常慢。
- 但你**不会**这么做——你用 `git log` / `git blame`，它们在内存里先建索引再回答。

SCIP 同理：`.scip` 文件本身不是查询对象，它通过加载到 Kuzu / PostgreSQL / 内存 map 之后才是查询对象。**这种"最小存储 + 按需建索引"的分层是经典做法**，不是 SCIP 的偷懒。

## 11. 一句话总结

SCIP 把代码的语义信息拆成两个正交维度：

- **位置面**（`Document.occurrences`）：每个标识符出现都有一条记录，配 0 基范围 + 符号字符串 + 角色位 + 包围范围。
- **符号面**（`Document.symbols`）：每个被定义的符号都有一份元数据档案，含文档、种类、出向关系。

两者通过**人可读、跨索引唯一的符号字符串**连接。**调用、继承、override 等"关系"不直接存边，而是从位置面或符号面派生**——这种"扁平 + 字符串主键 + 派生关系"的设计，让一份 `index.scip` 既能独立用，又能与其它索引拼接，还能流式生产/消费。
