# 014. CodeGraphContext 最终图数据模型（C# / scip-dotnet）

> 这份文档描述：当用户用 CGC 索引一个 C# 仓库（语言走 `scip-dotnet` 路径）后，**最终落到 KuzuDB 里的图长什么样**——节点、边、属性、来源、合并规则。
>
> 与协议层（013）和工具层（012）配套：
>
> - 013 讲 SCIP 协议本身的数据模型
> - 012 讲 `scip-dotnet` 怎么生成 SCIP
> - **014（本文）讲 CGC 把 SCIP 翻译成图后图里有什么**

---

## 0. 一句话定性

CGC 的图 = **"文件树 + 类型/方法节点 + 调用/继承/包含边"**，由 4 路数据源（SCIP 定义、SCIP 引用、SCIP 关系、Tree-sitter 补全）汇成，全部用 Cypher `MERGE` 语义写入 KuzuDB。C# 走专门的分支处理`is_implementation` 关系并通过 Tree-sitter 补充 `scip-dotnet` 不发的源码 / 圈复杂度 / 修饰器。

## 1. 数据流总览

```
                ┌───────────────────┐
                │  scip-dotnet CLI  │  → index.scip (Protobuf)
                └───────┬───────────┘
                        │
                ┌───────▼───────────────────────────────────────┐
                │  ScipIndexParser.parse(index_scip, project)   │
                │  ─────────────────────────────────────────    │
                │   ① 扫 occurrences (def)  → symbol_def_table  │
                │   ② 扫 SymbolInformation  → bases / docs      │
                │   ③ 推断 kind (suffix启发式,因 kind=0)        │
                │   ④ 扫 occurrences (ref) → call edges         │
                │      └─ 用 char_after=='(' 过滤               │
                │      └─ _find_enclosing_definition 找 caller  │
                └───────┬───────────────────────────────────────┘

                        │
                ┌───────▼─────────────────────────────────────────┐
                │  scip_pipeline.run_scip_index_async             │
                │  ───────────────────────────────────────────    │

                        │
                ┌───────▼───────┐
                │   KuzuDB 图   │
                └───────────────┘
```

## 2. 节点（Node Labels）

CGC 在 KuzuDB 里维护一个固定的节点 label 集合。C# 索引会用到的：

| Label | 数量级 | 主键三件套 | 来自 |
| :--- | :--- | :--- | :--- |
| **`Repository`** | 1（每仓库） | `path` | `add_repository_to_graph` 顶层加 |
| **`Directory`** | O(目录数) | `path` | `add_file_to_graph` 沿路径切分 |
| **`File`** | O(.cs 文件数) | `path` | `add_file_to_graph` 每个文件一份 |
| **`Class`** | O(class 数) | `(name, path, line_number)` | SCIP `kind=7` 或 suffix `#` |
| **`Interface`** | O(interface 数) | 同上 | SCIP `kind=20` 或源码以 `interface ` 开头 |
| **`Struct`** | O(struct 数) | 同上 | SCIP `kind=49` |
| **`Record`** | O(record 数) | 同上 | C# `record` |
| **`Enum`** | O(enum 数) | 同上 | SCIP `kind=18` |
| **`Function`** | O(method+ctor+local fn 数) | 同上 | SCIP `kind=17/26` 或 suffix `().` |
| **`Variable`** | O(field 数) | 同上 | SCIP `kind=15/61` |
| **`Parameter`** | O(参数数) | `(name, path, function_line_number)` | 每个 Function 的 `args` |
| **`Module`** | O(namespace 数) | `name` | TS supplement 的 imports |
| **`ExternalClass`** | O(外部父类数) | `name` | INHERITS 解析时父类不在工作区 |

> ⚠️ **C# 没有独立的"Method" label**。普通方法、构造函数、析构函数、局部函数全部入 `Function`。是不是成员方法靠 `class_context` 属性区分。

### 2.1 主键策略

绝大多数代码符号节点都用 `(name, path, line_number)` 三元组作主键（Cypher MERGE 语义）。这意味着：

- 同名方法（重载）按 `line_number` 区分
- 同名方法在不同文件按 `path` 区分
- 类内成员的 `path` 与类的 `path` 相同（同一文件）

不像 SCIP 用全局唯一的符号字符串，CGC 落到图里时**丢弃了 SCIP symbol 串本身**——只保留文件 + 行号 + 名字组成的"位置坐标"。

## 3. 节点的属性

不同 label 属性集略有差异，以下是典型 C# 索引会落的属性（来自 `@d:/ai-lab/CodeGraphContext/src/codegraphcontext/tools/scip_indexer.py:612-648`）：

### 3.1 通用属性（所有代码符号节点）

| 属性 | 类型 | 来源 |
| :--- | :--- | :--- |
| `name` | string | `_name_from_symbol(scip_symbol)` 抽出标识符 |
| `path` | string | 文件绝对路径 |
| `line_number` | int | SCIP `occurrence.range[0] + 1` |
| `end_line` | int | SCIP 不给结束行，默认等于 `line_number`（**TS 补会更新**） |
| `lang` | string | `"c_sharp"`（ScipIndexParser._lang_from_path） |
| `is_dependency` | bool | 是否来自依赖（用户索引主仓库时为 false） |
| `docstring` | string\|null | SCIP `SymbolInformation.documentation` 拼接（含 `cs 代码块` + XML 文档） |

### 3.2 `Function` 节点专属

| 属性 | 类型 | 来源 |
| :--- | :--- | :--- |
| `args` | list[string] | 由 `_parse_signature` 从 documentation 抽出 |
| `return_type` | string\|null | 同上 |
| `class_context` | string\|null | 如 `App.Greeter`（成员方法），非成员为 null |
| `cyclomatic_complexity` | int | 默认 1，**Tree-sitter 补会覆盖** |
| `decorators` | list[string] | 默认 []，**Tree-sitter 补会覆盖**（如 `[Obsolete]`） |
| `source` | string\|null | 默认 null，**Tree-sitter 补**（整段源代码） |
| `context` | string\|null | 嵌套方法的外层方法名 |
| `context_type` | string\|null | 如 `function_definition` |

### 3.3 `Class` / `Struct` / `Record` / `Interface` 节点专属

| 属性 | 类型 | 来源 |
| :--- | :--- | :--- |
| `bases` | list[string] | SCIP `Relationship.is_implementation` 列表（已扁平化为名字列表） |
| `context` | string\|null | 嵌套类的外层 |
| `source` | string\|null | **Tree-sitter 补**整段源代码 |

> 注意：`bases` **同时包含父类和接口**——`scip-dotnet` 在符号信息里把它们都标 `is_implementation=true`（见 012 §4.4）。CGC 在写 INHERITS/IMPLEMENTS 边时才二选一区分。

## 4. 边（Relationship Types）

| Edge | 起点 | 终点 | 由谁写 | 何时写 |
| :--- | :--- | :--- | :--- | :--- |
| **`CONTAINS`** | Repository / Directory / File / Class | Directory / File / Function / Class / ... | `add_file_to_graph` | 每文件入图时 |
| **`CALLS`** | Function / Class / Interface ... 或 File | Function / Class / Interface ... | `write_scip_call_edges` | 全部文件写完后 |
| **`INHERITS`** | Class / Record / Interface / Struct | Class / Record / ExternalClass | `_create_csharp_inheritance_and_interfaces` | inheritance pass |
| **`IMPLEMENTS`** | Class / Struct / Record | Interface | 同上 | 同上 |
| **`IMPORTS`** | File | Module | `add_file_to_graph` | 每文件入图时（来自 TS） |
| **`HAS_PARAMETER`** | Function | Parameter | `add_file_to_graph` | 每文件入图时 |

### 4.1 `CONTAINS` 的层次

```
Repository ─CONTAINS→ Directory ─CONTAINS→ Directory ─CONTAINS→ File
                                                                  │
                                                                  ├─CONTAINS→ Class ─CONTAINS→ Function
                                                                  ├─CONTAINS→ Function (顶层)
                                                                  ├─CONTAINS→ Variable
                                                                  └─CONTAINS→ Interface ...
```

`File ─CONTAINS→ Function` 总会建。`Class ─CONTAINS→ Function` 在方法的 `class_context` 非空时额外建（`@d:/ai-lab/CodeGraphContext/src/codegraphcontext/tools/indexing/persistence/writer.py:274-293`）。

### 4.2 `CALLS` 的属性

```cypher
MERGE (caller)-[:CALLS {line_number: $ref_line, source: 'scip'}]->(callee)
```

`source='scip'` 标识"这条边来自 scip-dotnet 路径"——区别于 Tree-sitter 兜底路径。`line_number` 是**调用点的行**，不是 caller 自己的定义行。

### 4.3 `INHERITS` 的两种来源

| 来源 | `confidence_label` | 触发 |
| :--- | :--- | :--- |
| 工作区内父类 | `'EXTRACTED'` | 父类节点也在图里 |
| 工作区外父类 | `'INFERRED'` | 父类用 `ExternalClass` label 占位 |

CGC 对 C# 用专门分支处理（`@d:/ai-lab/CodeGraphContext/src/codegraphcontext/tools/indexing/persistence/writer.py:582-645`）——见 §6。

### 4.4 `IMPLEMENTS` vs `INHERITS` 的判别

C# 里 `is_implementation` 关系既可能是"实现接口"也可能是"继承类"。CGC 的判别（`@d:/ai-lab/CodeGraphContext/src/codegraphcontext/tools/indexing/persistence/writer.py:603-618`）：

```python
is_interface = False
for iface in file_data.get("interfaces", []):
    if iface["name"] == base_name:
        is_interface = True
        break

# C# 规则：第一个基类如果不是 interface 则是父类，其余必为 interface
if is_interface or (base_index > 0 and type_label == "Class"):
    # IMPLEMENTS
else:
    # INHERITS
```

两条规则：

1. 如果 `base_name` 在本文件已识别为 `Interface` → IMPLEMENTS
2. 否则若它不是第一个基类，又当前类是 Class → IMPLEMENTS（C# 单继承规则：第一个非接口才是父类）
3. 都不是 → INHERITS

> ⚠️ 这个启发式有边界情况：跨文件的接口（`base_name` 不在本文件）只能靠第 2 条命中——所以 `Foo : OtherFile.IBar` 只有当 `IBar` 不是第一个基类时才会被识别成 IMPLEMENTS，否则会被错误地归类成 INHERITS。

## 5. 4 路数据源的合并

CGC 的图节点 / 边由 4 个独立数据流汇聚而成。理解这点对调试"为什么图里少了某个属性"很关键。

### 5.1 数据源 ① ：SCIP 定义 occurrence

来自 `scip-dotnet` 的 `Occurrence{symbol_roles & 1 == 1}`。**决定节点的存在性和位置**。

| 属性写出 | 由 ① |
| :--- | :--- |
| `name`、`path`、`line_number`、`lang` | ✅ |

### 5.2 数据源 ② ：SCIP `SymbolInformation`

来自 `scip-dotnet` 的 `Document.symbols` 数组。**决定节点的元数据**。

| 属性写出 | 由 ② |
| :--- | :--- |
| `docstring`（拼接 documentation 数组） | ✅ |
| `kind`（推断节点 label） | ✅ 但 scip-dotnet 全发 0，**实际靠后缀启发式** |
| `bases`（取 `Relationship.is_implementation` 列表） | ✅ |
| `args` / `return_type` | ✅ 从 documentation 字符串解析（如 `string Greeter.Hello(string name)`） |

### 5.3 数据源 ③ ：SCIP 引用 occurrence + 启发式

来自 `Occurrence{symbol_roles == 0}`，配合**源码文本**和 `_find_enclosing_definition`。**决定 CALLS 边**。

详细逻辑见 011 §4 和上一份回答；此处不展开。

### 5.4 数据源 ④ ：Tree-sitter 补全

`scip_pipeline.run_scip_index_async` 第 86-130 行，**对每个 SCIP 索引到的文件再用 Tree-sitter 解析一次**，把缺失的字段补回去：

| 属性写出 | 由 ④ |
| :--- | :--- |
| `source`（整段源代码） | ✅ scip-dotnet 不给 |
| `cyclomatic_complexity` | ✅ scip-dotnet 不给 |
| `decorators` | ✅ scip-dotnet 不给 |
| `imports` | ✅ 替代 SCIP 的 namespace（CGC 直接用 TS 的） |
| `variables` | ✅ 替代（C# 字段更适合 TS 的口径） |
| `bases`（如果 SCIP 没识别） | ✅ 兜底 |

更进一步：如果某个 .cs 文件在 SCIP 索引产物里没出现（如 `dotnet restore` 失败的项目），SCIP 流水线会**额外用 Tree-sitter 单独索引这些文件**（`@d:/ai-lab/CodeGraphContext/src/codegraphcontext/tools/indexing/scip_pipeline.py:142-183`），保证图谱不漏文件——但这些"补丁文件"上的节点不会带 `source='scip'` 的 CALLS 边。

## 6. C# 路径的特殊化处理

`scip-dotnet` 用旧版 SCIP 协议 + Roslyn 的若干特性，导致 CGC 走专属分支处理。

### 6.1 `kind=0` → suffix 启发式

`scip-dotnet` **不发** `SymbolInformation.kind`，所有符号都是 `UnspecifiedKind=0`。CGC 在 `@d:/ai-lab/CodeGraphContext/src/codegraphcontext/tools/scip_indexer.py:528-549` 用符号字符串后缀启发式补：

| Symbol 后缀 | 推断为 | 二次启发式 |
| :--- | :--- | :--- |
| `#` | Class (`kind=7`) | 如果源码该行以 `interface ` 开头 → Interface (`kind=20`) |
| `().` 且含 `#` | Method (`kind=26`) | — |
| `().` 不含 `#` | Function (`kind=17`) | — |

### 6.2 Event 误判为 Class（已知 false positive）

`scip-dotnet` 把 C# 的 `event` 也用 `#` 后缀（见 012 §5.1）。CGC 启发式只看后缀 → 把每个 event 当成一个 `Class` 节点入图。

**症状**：图里多出一些"伪 class"节点，名字像 `MyEvent`、`Click`，没有真实方法 / 字段。

### 6.3 反引号转义名字 → 解开

`scip-dotnet` 把含特殊字符的名字（如 ctor `.ctor`、终结器 `~Greeter` 在 SCIP 里是反引号 `` `~Greeter` ``）反引号包起来。CGC `_name_from_symbol` 在 `@d:/ai-lab/CodeGraphContext/src/codegraphcontext/tools/scip_indexer.py:696` 用 `re.sub(r"^\`([^\`]+)\`$", r"\1", name)` 还原成 `.ctor`、`~Greeter`。

### 6.4 `is_implementation` 单标志 → INHERITS / IMPLEMENTS 二选一

见 §4.4。

### 6.5 调用边走 fallback 路径

`scip-dotnet` 不发 `Occurrence.enclosing_range`，CGC `_find_enclosing_definition` 走 fallback 启发式（见上一回答）：**用"距离引用行号最近的、上面的、以 `).` 结尾的方法定义"** 作为 caller。在 lambda、嵌套类、嵌套方法、表达式属性体里可能错位。

### 6.6 C# 文件被推迟到专门的 inheritance pass

```@d:/ai-lab/CodeGraphContext/src/codegraphcontext/tools/indexing/resolution/inheritance.py:79-82
    for file_data in all_file_data:
        if file_data.get("lang") == "c_sharp":
            csharp_files.append(file_data)
            continue
```

通用 inheritance 解析器（用 `imports_map` 跨文件解析父类位置）**对 C# 不工作**——C# 的 `using` 和命名空间映射规则太复杂。CGC 把 C# 文件单独抠出来，最后调 `_create_csharp_inheritance_and_interfaces`：跨文件查 `MATCH (parent:... {name: $parent_name})` 不带 path 限定，只靠**名字全局匹配**。

> ⚠️ **副作用**：若工作区有两个同名 class（罕见但可能），父类匹配会随机选一个。这是为了规避 C# 命名空间解析复杂度的折中。

## 7. 走查实例

### 7.1 源代码

`Greeter.cs`（在仓库 `d:/repo`）：

```csharp
namespace App;

public interface IGreeter
{
    string Hello(string name);
}

public class Greeter : IGreeter
{
    public string Hello(string name) => Format(name);
    private string Format(string s) => $"hi {s}";
}
```

### 7.2 索引后图谱

**节点**（含主要属性）：

| label | name | path | line | 关键属性 |
| :--- | :--- | :--- | :---: | :--- |
| Repository | `repo` | `d:/repo` | — | `name="repo"` |
| Directory | `repo` | `d:/repo` | — | （可能不存在,看是否分目录） |
| File | `Greeter.cs` | `d:/repo/Greeter.cs` | — | `lang="c_sharp"` |
| Interface | `IGreeter` | `d:/repo/Greeter.cs` | 3 | `bases=[]`, `docstring="```cs\ninterface IGreeter\n```"` |
| Function | `Hello` | `d:/repo/Greeter.cs` | 5 | `class_context="IGreeter"`, `args=["name"]`, `return_type="string"` |
| Class | `Greeter` | `d:/repo/Greeter.cs` | 8 | `bases=["IGreeter"]` |
| Function | `Hello` | `d:/repo/Greeter.cs` | 10 | `class_context="Greeter"`, `args=["name"]` |
| Function | `Format` | `d:/repo/Greeter.cs` | 11 | `class_context="Greeter"`, `args=["s"]` |
| Parameter | `name` | `d:/repo/Greeter.cs` | function_line=5 | （IGreeter.Hello 的形参） |
| Parameter | `name` | `d:/repo/Greeter.cs` | function_line=10 | （Greeter.Hello 的形参） |
| Parameter | `s` | `d:/repo/Greeter.cs` | function_line=11 | — |

**边**：

```
Repository{repo} ─CONTAINS→ File{Greeter.cs}
File{Greeter.cs} ─CONTAINS→ Interface{IGreeter, line=3}
File{Greeter.cs} ─CONTAINS→ Function{Hello, line=5}        # IGreeter.Hello
File{Greeter.cs} ─CONTAINS→ Class{Greeter, line=8}
File{Greeter.cs} ─CONTAINS→ Function{Hello, line=10}        # Greeter.Hello
File{Greeter.cs} ─CONTAINS→ Function{Format, line=11}

Interface{IGreeter} ─CONTAINS→ Function{Hello, line=5}
Class{Greeter} ─CONTAINS→ Function{Hello, line=10}
Class{Greeter} ─CONTAINS→ Function{Format, line=11}

Function{Hello, line=5} ─HAS_PARAMETER→ Parameter{name, function_line=5}
Function{Hello, line=10} ─HAS_PARAMETER→ Parameter{name, function_line=10}
Function{Format, line=11} ─HAS_PARAMETER→ Parameter{s, function_line=11}

Class{Greeter} ─IMPLEMENTS→ Interface{IGreeter}             # 来自 SCIP is_implementation
Function{Hello, line=10} ─CALLS {source='scip'}→ Function{Format, line=11}   # 重建调用边
```

注意 **3 个 Function `Hello`** 不冲突（不同 line，主键不同）。**Class.Greeter ─IMPLEMENTS→ Interface.IGreeter** 这条边能精确建立是因为 `IGreeter` 在同文件被识别成 Interface 节点（§4.4 第 1 条规则命中）。

### 7.3 哪些字段来自哪条数据源

| 字段 | 数据源 | 备注 |
| :--- | :---: | :--- |
| 节点存在 + name + line | ① SCIP def | — |
| docstring | ② SCIP SymInfo | 含 cs 签名+无 XML 文档 |
| bases (`["IGreeter"]`) | ② SCIP relationship | `is_implementation=true` |
| args / return_type | ② SCIP SymInfo | 从 documentation 字符串解析 |
| `Greeter.Hello → Format` CALLS | ③ SCIP ref + 启发式 | char_after='(' + fallback caller |
| `Class IMPLEMENTS Interface` | ② → §4.4 解析 | base_name 命中本文件 Interface |
| `cyclomatic_complexity / source / decorators` | ④ Tree-sitter | scip-dotnet 不给 |

## 8. 与 SCIP 协议的对照

| SCIP 协议字段 | 在 CGC 图里的形态 |
| :--- | :--- |
| `Document.relative_path` | `File.path`（拼成绝对路径）+ `File.relative_path` |
| `Occurrence.range[0]` | `Function/Class.line_number = range[0]+1` |
| `Occurrence.symbol_roles & 1` | 决定走"建节点"还是"建 CALLS 边"分支 |
| `Occurrence.symbol` | **不入图**——CGC 用 `(name, path, line)` 主键，SCIP symbol 字符串只在解析期作内部 ID |
| `Occurrence.enclosing_range` | scip-dotnet 不发，CGC 走 fallback；新版索引器会用主路径 |
| `SymbolInformation.kind` | scip-dotnet 全发 0，CGC 用后缀启发式补 |
| `SymbolInformation.documentation` | `Function.docstring` / `Class.docstring`（拼接） |
| `SymbolInformation.relationships[is_implementation]` | `bases` list → INHERITS / IMPLEMENTS 边（§4.4 二选一） |
| `SymbolInformation.relationships[is_reference]` | **不读**（CGC 只用 is_implementation） |
| `Index.metadata.tool_info` | **不入图**（只在日志里看到） |
| `Index.external_symbols` | 只补 documentation/kind 到已存在节点；不创建外部节点（除非 INHERITS 解析时降级为 `ExternalClass`） |

## 9. 一句话总结

CGC 的最终图 = **(节点 ← SCIP def occurrence) + (节点元数据 ← SCIP SymbolInformation + Tree-sitter 补) + (CALLS 边 ← SCIP ref occurrence + char_after 启发式 + enclosing_range fallback) + (INHERITS/IMPLEMENTS 边 ← SCIP is_implementation 关系经 C# 专属解析器二选一) + (CONTAINS 边 ← 文件树 + class 结构) + (HAS_PARAMETER 边 ← Function args)**。

主键是 `(name, path, line_number)` 而不是 SCIP symbol 字符串——意味着图能独立做查询，不依赖 SCIP，但也丢掉了"跨索引拼接"这个 SCIP 协议核心能力。
